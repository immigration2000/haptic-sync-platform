# ★ 2026-11-21 — 보내주신 영상 확인했습니다

### 영상에서 출력 기기가 **30초 내내 한 번도 안 움직였습니다**

컨트롤러의 파란 LED 를 기준으로 영상을 정렬해 0.5초 간격 62장을 비교했는데
링키지 자세가 **전부 똑같습니다.** 소리에도 서보 돌아가는 소리가 없습니다.
(컨트롤러 전원은 들어와 있습니다 — 파란 LED 는 내내 켜져 있습니다)

즉 지금 보시는 건 **끊김이 아니라 아예 안 나가는 상태**입니다. 11-20 에 고친
타이밍 문제(지나간 값이 뒤에 나가던 것)와는 다른 원인입니다.

### 노트북 화면은 못 읽었습니다

화면 글씨가 너무 작아 읽히지 않습니다(여러 장을 겹쳐 선명하게 만들어 봐도 안 됐습니다).
그래서 **원인을 영상만으로 좁히지 못했습니다.** 아래 다섯 가지 중 어느 것인지
진단 창 숫자만 보면 바로 갈립니다:

| 가능성 | 진단 창에서 |
|---|---|
| 출력 기기가 안 붙어 있다 | 송신요청 0 · 생략 사유 **"출력 미연결"** |
| 입력은 붙었는데 수신이 0 | **수신 0** — notify 를 안 쏘거나 **줄 끝에 개행이 없음** |
| 복사 토글이 꺼져 있다 | 생략 사유 **"복사 꺼짐"** |
| 보내긴 하는데 기기가 무시한다 | 송신요청·**쓰기완료는 오르는데** 안 움직임 (포맷/드라이버 문제) |
| 값이 기기 범위 밖이다 | 위와 같은데 특정 축만 |

→ **진단 창의 "파일로 저장" 결과 하나만 보내주시면 됩니다.**
  사진으로 찍으실 거면 기기 말고 **노트북 화면만 가까이** 찍어주세요.

# ★ 2026-11-21 — 진단 창에 '축 위치' 막대가 생겼습니다

숫자만 봐서는 어디로 어떻게 움직이는지 모르겠다고 하셔서, **받은 값과 보낸 값을
그대로 막대와 그래프로** 그렸습니다. 새로고침(Ctrl+Shift+R) 하시면 보입니다.

축마다 두 줄입니다:

```
L0   수신  ████████████▌|              52.0%     ← 파랑
     송신  ████████████▌|              52.0%     ← 초록
     [최근 5초 곡선]
```

- **막대** = 지금 기기가 있어야 할 위치 (`I` 보간 반영)
- **흰 눈금** = 마지막으로 받은/보낸 목표값
- **곡선** = 최근 5초. 수신은 굵은 파랑, 송신은 가는 초록
- 오른쪽 위 **수신→복사 지연** = 받은 줄이 나가기까지 걸린 시간 (평균·최대)

### 보는 법

| 보이는 모습 | 뜻 |
|---|---|
| 초록 선이 파란 띠 **안에** 들어앉음 | 받은 걸 그대로 보내고 있다 — 정상 |
| 파란 띠만 있고 초록이 없다 | 받긴 받는데 **안 내보내고 있다** (복사 꺼짐/출력 미연결) |
| 막대가 아예 안 움직인다 | 수신 자체가 없다 — 기기가 안 쏘거나 **개행 누락** |
| 초록이 파란 띠 밖으로 비져나옴 | 그 구간이 유실·지연 |

### ★ 이게 왜 중요한가

**이 곡선은 "우리가 받고 보낸 값"입니다.** 기기가 실제로 이 곡선대로 움직이는지는 별개예요.
그래서 이제 이렇게 가를 수 있습니다:

- 곡선은 **매끄러운데** 기기가 덜컥거린다 → 문제는 **기기/펌웨어 쪽**
- 곡선 자체가 계단처럼 끊긴다 → 문제는 **우리 쪽**(또는 입력 기기 송신 주기)
- 곡선에 초록이 아예 없다 → **전달이 안 되고 있다**

영상 찍으실 때 이 화면이 같이 나오면 저희가 훨씬 많은 걸 읽을 수 있습니다.

# ★ 2026-11-20 갱신 — 끊김 관련 수정이 들어갔습니다

보내주신 분석서(생략 1,000회 초과 / 움직임 끊김) 확인했습니다. **원인 2개를 찾아 고쳤습니다.**
배포 완료, 서버 재시작 없음. **브라우저에서 Ctrl+Shift+R 로 한 번 새로고침** 해주세요
(스크립트 버전을 올렸지만 확실히 하기 위함입니다).

### 고친 것

1. **지나간 위치가 새 위치 뒤에 나가는 버그** — 가장 유력한 끊김 원인이었습니다.
   20ms 대기 중인 줄이 있는데 새 줄이 바로 나갈 수 있는 타이밍이 되면, 새 줄을 보낸 **뒤에**
   대기하던 **옛 줄**이 한 번 더 나갔습니다. 기기가 새 위치로 갔다가 옛 위치로 되돌아가니
   그게 덜컥거림으로 보입니다. 폰이 바쁠수록 심해집니다.

2. **진단 창이 스스로 부하를 만들고 있었습니다** — 저희 잘못입니다.
   로그를 보는 사람이 없어도 건별로 탭 간 전파를 쳤고, 100Hz 입력이면 초당 200건이었습니다.
   **"진단하려고 창을 열면 더 끊기는"** 구조였습니다. 이제 진단 창이 열려 있을 때만,
   묶어서 보냅니다(창을 닫으면 6초 안에 저절로 멈춤). 분석서의 측정값이 이것 때문에
   왜곡됐을 수 있어 **다시 측정해 주시면** 좋겠습니다.

3. **전송 간격을 기기 실제 속도에 맞춥니다** — 20ms 고정은 기기의 실제 쓰기 속도와
   관계없는 추측값이었습니다. 이제 **앞 쓰기가 끝난 뒤에** 보냅니다. 기기가 빠르면 더 빠르게,
   느리면 기기 속도로 갑니다. (쓰기 응답이 끝내 안 오면 300ms 뒤 그냥 보냅니다 —
   연결은 절대 버리지 않습니다)

4. **통계를 연결할 때마다 0 으로 초기화합니다.** 전엔 어제 수치가 섞여 있었습니다.

### 먼저 알아두실 것 — **생략 1,000회는 고장이 아닙니다**

생략은 BLE 오류나 기기 거부 횟수가 **아닙니다.** 20ms 안에 여러 줄이 오면 마지막 줄만
보내는 **설계된 동작**이고, 그때 버린 줄 수입니다. 입력이 100Hz면 **20초만 돌려도 1,000을 넘습니다.**
위치 명령이라 지나간 값은 버려도 되기 때문입니다. 보셔야 할 것은 생략 수가 아니라
아래 **쓰기대기** 입니다.

### 진단 창에 새 항목 4개

출력 기기 카드에 **송신요청 / 쓰기완료 / 쓰기실패 / 쓰기대기** 가 생겼습니다.

- **쓰기완료** — 실제로 전송이 끝난 수. 전엔 "송신"이 큐에 넣은 수라 실제 성공을 알 수 없었습니다
- **🔴 쓰기대기** — 이게 **계속 1 이상(주황색)이면 기기가 우리 전송 속도를 못 따라오는 것**입니다.
  이 값이 평소 0 이면 전송 경로는 정상입니다
- **쓰기실패** — 0 이 아니면 BLE 링크나 펌웨어 쪽 문제입니다

### 축마다 따로 줄로 보내셔도 됩니다 (이것도 고쳤습니다)

처음엔 "입력 포맷을 알려주셔야 고칠 수 있다"고 적었는데, **포맷을 몰라도 되게** 고쳤습니다.
이제 어느 쪽으로 보내셔도 맞게 동작합니다.

```
한 줄에 전 축    L0500I100 R1800I100     → 전체 상태로 보고 최신 줄만 보냅니다
축마다 따로 줄   L0500I100
                R1800I100               → 다른 축이므로 **둘 다 보냅니다** (전엔 하나가 버려졌습니다)
같은 축 연타     L0500I100 → L0600I100   → 최신값만 보냅니다 (위치라 그게 맞습니다)
DSTOP, D1       → 제어 명령은 서로 덮어쓰지 않습니다
```

즉 **생략에 다른 축이 희생되는 일은 이제 없습니다.** 같은 축의 지나간 값만 버립니다.

### ★ 이번에 부탁드릴 것 2개

**① 진단 창의 '타이밍' 숫자를 알려주세요** (새로 생겼습니다)

출력/입력 카드 옆에 **타이밍** 카드가 있습니다. 1초마다 갱신됩니다.

| 보이는 것 | 뜻 |
|---|---|
| **수신 Hz** | 기기가 실제로 보내는 주기 |
| **전송 Hz** | 실제로 출력 기기에 나간 주기 |
| **최대 / p95** | 간격이 튀는 정도. 평균보다 이쪽이 중요합니다 |
| **쓰기** | 전송 1건이 끝나는 데 걸린 시간(ms) — **이게 전송 주기의 한계**입니다 |

→ **수신 Hz 가 쓰기 시간보다 빠르면 생략이 나는 게 정상입니다.** (예: 쓰기 20ms인데 100Hz 입력)
  끊김이 남아 있다면 **쓰기 시간**과 **쓰기대기** 를 봐주세요.

**② 다시 측정해 주세요** — 위 2번(진단 로그 부하) 때문에 이전 측정값이 왜곡됐을 수 있습니다.
진단 창의 **파일로 저장** 을 누르고 그 파일을 보내주시면 됩니다.

(기존 부탁인 **rxChar UUID** 도 그대로 유효합니다 — 아래 2번)

자세한 내용: `patches/2026-11-20.md`

## 1. 요청 대비 구현 상태

| 요청 | 상태 | 비고 |
|---|---|---|
| `rxChar`(notify) 추가, 기기→브라우저 | ✅ | 서비스 UUID 는 기존과 동일하게 사용 |
| txChar/rxChar 각 1개, **2개 기기 동시 연결** | ✅ | `bleOutput`(기존) / `bleInput`(신규) 로 분리 |
| rx 로 들어온 신호를 tx 로 **그대로 복사** | ✅ | 내용 변형 없음. 전송 간격만 제한(아래 3-②) |
| rxChar UUID | ⏳ **미확정** | 지금은 **자동 탐색** 중 — 아래 2번이 핵심 부탁 |

기존 출력 경로(`txChar` 쓰기)는 **하나도 건드리지 않았습니다.** 플레이어·통화·콘솔 등
기존 기능은 그대로 동작합니다.

## 2. ★ 제일 먼저 부탁드릴 것 — rxChar UUID 확정

UUID 를 못 받아서, 지금은 **서비스 안에서 notify 가능한 캐릭터리스틱을 자동으로 고릅니다.**
연결할 때마다 브라우저 콘솔에 전체 목록을 찍습니다:

```
[PulseDevice] 서비스 캐릭터리스틱 목록:
  216f3732-6f41-4fde-98fa-e3033a2ace80 [write,writeWithoutResponse]
  xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx [notify]
[PulseDevice] 입력 캐릭터리스틱 자동 선택: xxxxxxxx-…
```

**이 목록을 알려주시거나, 직접 적어주셔도 됩니다:**

```
파일: ~/pulse/public/js/core/device_drivers.js
  ble: {
      service: '2d10a187-a483-4a60-8ca2-59b7d1704146',
      txChar:  '216f3732-6f41-4fde-98fa-e3033a2ace80',
      rxChar:  null,        ← 여기에 UUID 를 넣으면 자동탐색 대신 그걸 씁니다
      write:   'withoutResponse',
  },
```

자동 탐색도 동작하지만, **notify 가 여러 개면 첫 번째를 고르므로** UUID 를 박아두는 쪽이 확실합니다.

> 폰에서 직접 수정하시면 **알려만 주세요.** 저희가 git 에 그대로 반영합니다
> (수정분이 유실되지 않게 하기 위함입니다. 수정 자체는 괜찮습니다)

## 3. 알아두셔야 할 동작 3가지

요청서에 없던 부분인데, 실제로 돌리려면 필요해서 넣었습니다.

**① 줄 조립 (필수)**
BLE notify 는 MTU(보통 20바이트) 단위로 쪼개져 옵니다. 한 줄이 여러 알림에 걸쳐 오거나,
한 알림에 여러 줄이 들어옵니다. 그래서 **버퍼에 모아 개행(`\n` 또는 `\r`) 기준으로 잘라서** 처리합니다.

- → **기기 쪽에서 줄 끝에 개행을 붙여 보내주셔야 합니다.** 개행이 없으면 계속 버퍼에만 쌓이고
  아무것도 출력으로 나가지 않습니다 (깨진 조각을 기기로 보내는 것보다 낫다고 판단했습니다).
- 버퍼 상한 512바이트.

**② 전송 간격 20ms · 최신값만**
입력이 초당 수백 줄을 쏟으면 BLE 쓰기 큐가 끝없이 밀립니다. 위치 프로토콜이라
지나간 값은 의미가 없어서, **20ms 안에 여러 줄이 오면 마지막 줄만** 보냅니다.
생략한 수는 화면에 `(생략 N)` 으로 보입니다. 이 값이 계속 올라가면 입력 주기를 낮춰주세요.

**③ 출력과 같은 기기는 입력으로 못 붙입니다**
같은 기기를 양쪽에 붙이면 보낸 값이 되돌아와 무한 반복됩니다(물리 액추에이터라 위험).
`device.id` 로 막아뒀습니다. **서로 다른 기기 2대**로 테스트해 주세요.

- 출력/입력 상태, **수신·송신·생략·거부·오류를 한 화면에** 시간순으로 보여줍니다
- 종류별 필터 · 멈춤 · **복사 / 파일 저장** → 결과를 그대로 보내주시면 됩니다
- 수동 전송 칸에서 `L050I500` 같은 명령을 직접 쏴볼 수 있습니다
  ('검증 거쳐 전송'은 통화·방송에서 쓰는 검증기를 거칩니다 — 거부되는지 확인용)
- 이 창에서 기기를 직접 붙여도 되고, **다른 탭에서 테스트하면서 이 창으로 구경**해도 됩니다
  (단, 기기 연결 자체는 탭마다 따로입니다 — 브라우저 제약)

### 콘솔에서 쓸 수 있는 것 (F12 / 안드로이드는 USB 디버깅)

```js
PulseDevice.getInputStatus()        // {connected, label, rxCount, lastLine, relay, dropped}
PulseDevice.onInput(console.log)    // 수신되는 줄을 전부 찍기
PulseDevice.setRelay(false)         // 복사 끄기 (수신만 보기)
PulseDevice.setRelay(true)
PulseDevice.send('L050I500')        // 출력 기기로 직접 보내기 (출력만 따로 점검)
PulseDevice.disconnectInput()
```

## 5. 안 될 때 확인 순서

| 증상 | 확인 |
|---|---|
| 입력 기기 선택 창에 기기가 안 보임 | 다른 앱/탭이 그 기기를 이미 잡고 있지 않은지 |
| "notify 되는 캐릭터리스틱을 찾지 못했습니다" | 펌웨어가 notify 속성을 올리고 있는지. 콘솔의 캐릭터리스틱 목록 확인 |
| 연결은 됐는데 **수신 0** | 기기가 실제로 notify 를 쏘는지. 줄 끝 **개행** 이 있는지(3-①) |
| 수신은 느는데 **출력이 안 움직임** | 복사 토글이 켜져 있는지 / 출력 기기가 연결돼 있는지 / `PulseDevice.send('L050I500')` 가 먹는지 |
| `(생략 N)` 이 급증 | 입력 주기가 너무 빠름 — 기기 쪽 송신 주기를 낮춰주세요 |
| 카메라·화면 문제까지 겹침 | 고객센터 → **🧹 사이트 정리** (캐시·설정 초기화 후 자동 새로고침) |
