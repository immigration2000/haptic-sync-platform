## 2. 🔴 BLE-02 — 위치 역전 (확정 버그, 수정함)

`relay()` 의 즉시 송신 분기가 **대기 타이머를 정리하지 않았다.**

```
t=105  A 도착 → 대기, 타이머 t=120 예약
t=122  B 도착 → 20ms 지났으니 즉시 송신 (B)   ← 타이머가 그대로 살아있다
t=125  타이머 발화 → A 송신                    ← 지나간 위치가 나중에 나간다
```

출력 기기가 **B 로 갔다가 A 로 되돌아간다.** 위치 프로토콜이라 이것이 그대로
덜컥거림으로 보인다. 타이머는 `relayLastAt+20ms` 에 발화하도록 예약되지만 **메인 스레드가
밀리면 그 시점을 넘겨서 발화한다** — 그리고 다음 항목이 바로 그 '밀림'을 만들고 있었다.

→ 즉시 송신 전에 `clearTimeout` + 대기 줄 폐기. 폐기분은 `생략(새 값으로 대체)` 로 집계.

## 3. 🔴 진단 로그 발행이 스스로 부하를 만들었다 (`9727910` 회귀 — 우리 잘못)

`devLog()` 가 **구독자 유무와 무관하게 건별로** `BroadcastChannel.postMessage()` 를 쳤다.
100Hz 입력이면 수신·복사·생략 합쳐 **초당 약 200건**이고, `postMessage` 는 구조화 복제라
같은 출처의 **모든 문서**로 복사된다. 진단 창을 열면 거기서 DOM 행까지 그린다.

즉 **"진단하려고 창을 열면 더 끊기는"** 구조였다. 작업자에게 진단 창을 쓰라고 안내했으니
인계서의 측정값 자체가 오염됐을 가능성이 있다.

→ ① 다른 탭의 진단 창이 **2초마다 생존을 알릴 때만** 내보낸다 (TTL 6초)
  ② 건별이 아니라 **100ms 단위로 묶어** 한 번만 보낸다 (200/s → 10/s, 구독자 없으면 0)
  진단 창을 닫으면 6초 안에 발행이 저절로 멈춘다. 같은 문서의 진단 창은 `logListeners` 로
  직접 받으므로 이 경로와 무관하다 (그래서 자기 `ctxId` 의 알림은 셈에서 뺀다).

## 4. BLE-03 — 고정 20ms → **쓰기 완료 기준 배압**

20ms 는 기기의 실제 쓰기 속도와 아무 관계가 없는 추측값이다. 쓰기가 그보다 느리면
`bleWriteQueue` 가 끝없이 쌓여 움직임이 **점점 늦어진다.**

→ `writeInFlight`(큐에 넣었지만 아직 끝나지 않은 쓰기)를 보고, 앞 쓰기가 끝난 뒤에 보낸다.
  기기가 빠르면 20ms 로, 느리면 기기 속도로 간다. `RELAY_MIN_MS` 는 안전 하한으로만 남는다.

⚠ **안전장치 필수** — GATT 쓰기가 끝내 안 돌아오면 릴레이가 영구히 멈춘다.
예전에 write 를 기다리다 포트를 버리는 fail-closed 로 "스트로크 제어를 건드리면 연결이
끊긴다" 사고가 났다(§7). 그래서 `RELAY_STALL_MS = 300` — 쓰기가 안 끝나도 300ms 뒤엔
그냥 보낸다. **연결은 절대 버리지 않는다.**

쓰기 큐 자체에는 손대지 않았다. 배압은 **릴레이 경로에만** 건다 — 정지·초기화 같은
제어 명령이 버려지면 안 되기 때문이다 (인계서 §6 과 같은 판단).

## 5. BLE-04 · BLE-05 — 측정

- 입력 **연결 시** `rxCount`·`dropped`·`relayLastAt`·대기 줄을 초기화한다.
  해제 시점에는 남겨둔다(마지막 수치를 읽을 수 있게). "생략 1,000회"가 지금 것인지
  어제 것인지 구분이 안 됐던 문제.
- `getStatus()` 에 `writeOk`(쓰기 **완료**) · `writeErr` · `queued`(대기) 추가.
  진단 창 출력 카드에 **송신요청 / 쓰기완료 / 쓰기실패 / 쓰기대기** 로 표시한다.
  → **쓰기대기가 계속 1 이상이면 기기가 우리 전송 속도를 못 따라오는 것**이다(주황색).

## 6. BLE-07 은 보류 — 입력 포맷을 모른다

입력이 **축마다 별도 줄**로 온다면(`L0500I100\n` 다음 `R1800I100\n`) 20ms 병합이
**다른 축을 통째로 버린다.** 지나간 값을 버리는 게 아니라 **다른 축의 최신값**을 버리는 것이라
해당 축이 멈춘 것처럼 보인다. 한 줄에 전 축이 들어오면 지금 동작이 맞다.

→ 작업자에게 **진단 창의 '수신' 줄 10개**를 요청했다. 축마다 별도 줄이면 축 접두사별로
  최신값을 유지하도록 고친다(내용은 그대로 복사 유지). **포맷 확인 전에 바꾸지 않는다** —
  한 줄이 전체 상태인 경우 축별 분리가 오히려 상태를 깨뜨린다.

## 7. 하지 않은 것

- **`RELAY_MIN_MS` 를 낮추지 않았다.** 인계서 §6 판단에 동의한다 — 출력이 느리면 큐만 더 밀린다.
  4번이 들어간 뒤로 이 상수는 안전 하한일 뿐이라 낮출 이유도 줄었다.
- 쓰기 큐에 길이 제한을 걸지 않았다 (제어 명령 유실 위험).
- `device_drivers.js` 의 `rxChar` 는 여전히 `null`(자동 탐색) — UUID 미확정.

신설 테스트가 지키는 것(기능이 아니라 **타이밍**을 본다):

| 본 것 | 어떻게 |
|---|---|
| 지나간 줄이 새 줄 뒤에 안 나간다 | 타이머 발화를 테스트가 쥐고 있다가 **늦게** 발화시킨다 |
| 느린 기기(쓰기 60ms)에 큐가 안 쌓인다 | 60줄 입력 중 13줄만 나가고 대기 최대 **1** |
| 응답 없는 기기에도 대기가 폭증하지 않는다 | 40줄 입력, 대기 최대 **4**. 풀리면 최신값으로 즉시 복귀 |
| 통계가 이전 연결과 안 섞인다 | 재연결 후 `rxCount`·`dropped` 0 |
| 요청과 완료를 구분해 센다 | 쓰기 지연 중 `sentCount` 1 / `writeOk` 0 / `queued` 1 |
| 구독자 없으면 로그를 안 내보낸다 | 50건 → 0건. 구독 후 50건 → **1 메시지** |

**실제 브라우저**(로컬 서버 + 탭 2개): 50건이 1 메시지로 묶여 전달, 중복 0,
`[다른 탭]` 꼬리표 정상, 진단 창을 닫은 뒤 200건 발행 **0건**(로컬 링버퍼는 계속 기록).

❌ **실기기 2대 검증은 여전히 못 했다** — 기기가 없다. 작업자 확인 필요.
